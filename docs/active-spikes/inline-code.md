# Inline Code Highlighting
## Purpose
Extend the existing code-block syntax colors to inline code. The user chose Enzo as the implicit default, fragment support, and an optional per-snippet language/plain-text override. There is no language inference or article-wide setting.
## Approach
Highlight inline code while normalizing CMS content for SSR/static generation. Reuse the existing Enzo grammar, bundled languages, and three Shiki themes; emit all theme colors once so the current page theme recolors tokens through CSS. Preserve the original code text and surrounding HTML, and exclude code inside preformatted blocks. Keep a readable plain fallback for unknown languages and intentionally plain snippets.

Extend WordPress’s native Inline Code format with a `data-code-language` attribute and a small language control. Default snippets need no metadata. Keep the original editor toggle, normal text selection, and authored inline semantics. Editor syntax coloring is outside this slice; authoring clarity matters more than visual parity.

The first contrast check found that the original inline grounds were too light for several reused token colors. The user requested darker inline backgrounds as the first correction. Keep foreground colors and typography intact, and darken the scanline/glow layers where they brighten the backdrop enough to undermine dim operators or comments. This trial remains subject to visual review; validate contrast against the complete inline surface rather than assuming block palettes transfer safely.

Code-block reading feedback also belongs in this theme work: reuse the site's text cursor for code and preformatted text, and give native code-block selections a readable background and foreground drawn from the active code theme. Keep this local to the existing cursor rules and code-block recipe; syntax tokenization, inline surfaces, and theme controls retain their current behavior.
A 2026-10-17 trial extends precomputed theme colors to code blocks so a theme switch can interpolate the existing token nodes instead of replacing their HTML. Use a short 280ms CSS color blend, including the CRT surface tints, with an immediate reduced-motion fallback. Inline token colors follow the same clock. Keep text, native selection, and layout stable. The user positively reviews the existing blend on 2026-10-18; it remains the default while a separately requested reverse-hue comparison is explored.
## Reverse-hue comparison — 2026-10-18
The user requests an optional reverse color-wheel transition inspired by pixel-art palette cycling. Keep the accepted 280ms blend as the default. A small floating **Reverse hue cycle** checkbox appears on local desktop previews containing code blocks; it changes how the ordinary theme dots animate, rather than continuously rotating an idle theme. The red-to-yellow example follows decreasing HSL hue through magenta, purple/blue, and green instead of orange. Other color pairs follow that same decreasing-hue direction. This is a comparison, not an accepted replacement.

The first comparison used a single inherited numeric animation to drive CSS `color-mix(in hsl decreasing hue, …)` for the existing block/inline token nodes and block CRT surface colors. Capture currently painted colors before canceling an earlier cycle, so rapid changes restart from the visible palette. Theme endpoints come from the same precomputed token values and shared block surface configuration as the normal blend. Temporary properties are removed on completion, checkbox-off, route navigation, or reduced-motion changes; reduced motion and unsupported color mixing bypass the experiment. Selection colors remain the chosen theme’s normal selection treatment. The checkbox is off by default, stays in page state across local navigation, and is hidden outside local previews, on pages without code blocks, and on phone where the ordinary theme selector is already hidden.
The subsequent review finds near-identical hue endpoints asymmetric and the blue-entry magenta flash too strong, while larger blocks make the concept appealing. The revised trial keeps one inherited clock but gives every token a full reverse turn over 420ms around a shortest-hue OKLCH endpoint blend. Chroma drops by up to 25% in the middle; block shell roles blend directly in OKLab to avoid a large colored-background flash. Temporary transition suppression during cleanup prevents the ordinary 280ms blend from starting again. The TOC exempts this specific non-geometric root clock from its conservative ancestor-motion visibility gate. Six native direction checks pass with unchanged token DOM and exact final theme colors. The reverse option remains opt-in. Code-block shader unification with the Side Projects field remains an idea; the accepted resting code recipe is preserved.

## Accepted reverse hue cycle — 2026-10-19

## Rotating shell and optional token softening — 2026-10-19
Human feedback asks to retain the reverse hue path on the background, shaping its magenta segment rather than replacing it with a direct blend. All shell roles now rotate alongside tokens. A smooth hue-local curve centered at 330° lowers shell lightness by up to 10% and chroma by up to 40%, with the correction tapering to zero at both endpoints. This is an OKLCH detour through quieter purple, not an RGB Bézier implementation. Tokens retain full chroma by default. A local persistent Soften token hue cycle checkbox restores the former 25% middle-chroma reduction for comparison; it does not alter the shell path. Resting palettes, markup, selector behavior and reduced-motion handling remain unchanged. These refinements await human review.
