## Ranked Experimental Candidates
Historical candidate identifiers below are retained for continuity, not a currently approved ranking. E1–E3 now govern selection. Resource costs do not establish user-visible harm.

### A1 — Evaluate speculative case-study image readiness
High confidence in the cost and source path; exact achievable savings unmeasured. At 1440px, Home requested all five 1200px card treatments plus four 1800px treatments and an original USCIS image. The latter five total 21,961,644 bytes, a substantial speculative payload; do not equate all of it with removable bytes because a later detail navigation may need those assets. `useContentDetailPrefetch.ts` warms images before its static-data guard, assumes `sizes='100vw'`, and `CaseStudyCard.vue` triggers within a 1400px root margin while rendered cards use a narrower desktop size.

First measure the existing policy's contribution to reveal readiness and any interference with current-page loading. Later alternatives could include request-priority changes, different warm timing, or different size selection, but hover-only warming may harm immediate touch navigation. Keeping or expanding eager warming is valid if it improves the experience. Keep a clear policy with named functions, not a generalized scheduling framework. Readability cost low for small policy changes; regression risk moderate because card-to-detail readiness is intentional. Measure cold/warm click readiness in both transition directions. This is reusable delivery policy, so it is largely independent of content-audit edits.

### A2 — Give the homepage portrait a responsive delivery path
High confidence: both widths request the same 2,982,799-byte CMS PNG. `pages/index.vue` renders its URL without `srcset`, while the fallback WebP does not help when the CMS portrait is set. Test exposing existing WordPress size metadata and choosing appropriate candidates before introducing a new image pipeline; inspect generated sizes for the current portrait. Potentially meaningful on narrow screens; no guessed compression ratio. Readability cost low-to-moderate (small explicit data-model extension); preserve crop, alt text, and art direction. Systemic fix survives portrait replacement, unlike one-off CMS image edits.

### A3 — Separate code-theme metadata from the highlighting runtime
High confidence in bundling leakage, medium confidence in removable bytes. The 243,644-byte `useCodeTheme` chunk is requested on Home, Enzo, USCIS, and Side Projects; Writing does not request it. `BlockRenderer.vue` imports `CODE_THEME_SURFACES` and `useCodeTheme.ts` imports `CODE_THEME_LABELS` from `syntax-highlighting.ts`, which also imports Shiki. This gives non-code content a dependency on the highlighting module. The build manifest identifies this shared chunk; its generated contents include the highlighting/regex machinery.

First test a small dependency-free theme metadata module, leaving actual highlighting behind the CodeBlock boundary. Do not remove authoring languages or theme switching to obtain a smaller number. The entire 243 KB is not promised savings; rebuild and compare loaded chunks, initial highlighted output, and theme changes. Readability cost low, with a natural metadata/runtime separation; content-audit dependence low. Shiki's full distribution contains lazy language chunks, so the 10 MB build inventory is not a 10 MB page download ([official bundle documentation](https://shiki.style/guide/bundles)).

### B1 — Stop settled/offscreen card motion work
High confidence that `CaseStudyCard.vue` continuously reads dimensions and writes three CSS properties per enabled card; medium confidence in the fraction of measured homepage cost it explains. Candidate cumulative micro-optimizations: stop after convergence, restart on changed targets, gate offscreen work, and avoid repeated DOM queries/dimension reads where a simple cached reference suffices. These should be tested as small reversible changes; only add ResizeObserver machinery if needed for correct responsive geometry. Readability cost low-to-moderate; preserve motion character, pointer/focus behavior, resize correctness, and reduced-motion handling. Measure idle task/layout counts and interaction traces, not just FPS. No article-content dependency.

### B2 — Avoid preloading every reaction-diffusion seed
All five PNG seeds appear as link-initiated resources on Home: 567,950 unique body bytes; the component selects one seed at runtime. Depending on selection, the four others represent 384,406–508,309 bytes of candidate avoidable initial resource bodies, not proven wire savings. The eager URL glob makes all seeds build dependencies. Enzo also requests homepage-related chunks and seed preloads, so this may affect speculative route loading beyond Home. Establish the precise Nuxt/Vite prefetch chain before changing it. Prefer a readable asset-loading adjustment over custom bundler internals. Cost moderate; preserve SSR safety, random compositions, and procedural fallback. Independent of CMS editorial cleanup.

### C — Lower priority or content-dependent
- Heavy halftone PNG derivatives remain expensive even after speculative downloads are reduced. Compare visually equivalent encoding on a representative image before adopting another format; texture fidelity and automated regeneration matter. Benefit plausibly large but unmeasured; pipeline complexity moderate. Do not manually rewrite CDN URLs or silently alter the look.
- Side Projects requests two inline PNGs totaling 3,673,791 bytes at both widths. A generic responsive block-media audit may help, but one-off image/copy/layout repair belongs to the human-led content audit. Recheck after content settles; no editorial cleanup is scheduled here.
- Fonts: external CSS `@import` adds a discovery dependency; a homepage sample observed a successful ~229 ms stylesheet request and six successful Google font responses. Existing fonts already use `display=swap`. Consider earlier stylesheet discovery/preconnect only after a throttled waterfall establishes benefit; do not remove needed weights or self-host fonts without checking licensing/maintenance implications.
- Repeated `_payload.json` resource entries require request/cache attribution, not automatic deduplication work. Local preview delivery differs from Bunny. Inspect a matching deployed artifact's cache headers and actual completed requests before treating it as an application bug.
- Temporary editorial PNGs and fallback assets increase build/deploy storage. They were not among the measured page requests; cleanup is not currently a page-speed recommendation.

## Not Recommended From This Audit
- No framework rewrite, service worker, generalized prefetch engine, broad memoization pass, blanket CSS extraction, or language whitelist. No measured evidence justifies their maintenance burden.
- Do not optimize static visitor performance by tuning CMS/server caches first: the static guards already bypass those requests. Existing request deduplication, lazy block imports, media lazy loading, visibility handling, and responsive card derivatives are useful foundations to preserve.
- Do not treat inline CSS size alone as waste; critical rendering versus repeat-navigation reuse is a tradeoff to measure. Do not delete unrequested assets and claim a faster first paint.
- Do not postpone experience-first investigation solely because content audit comes later. Shared delivery/dependency boundaries should survive editorial changes. After content audit, rerun representative interaction journeys plus any newly heavy page instead of freezing today's content into permanent budgets.
