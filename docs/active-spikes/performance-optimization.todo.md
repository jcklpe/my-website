## Image Variant Consolidation Review — 2026-09-14
The user asked whether fewer image versions could improve the experience beyond warming the correct version. Yes, fewer distinct downloads per journey are worth considering, but deleting generated files and reducing visitor requests are different operations.

### Why Multiple Versions Exist
- **Original versus treatment:** CMS originals support editing/rebaking and potentially other uses; baked halftones put the expensive visual treatment into prepared assets. The source original is not necessarily the right public display asset. Preserve originals; avoid unnecessary public warming of them where a baked treatment is what will be displayed.
- **Three responsive widths:** both `scripts/bake-case-study-halftones.mjs` and `apps/cms/wp-content/plugins/project-bootstrap/includes/halftone-media.php` define 600, 1200, and 1800px derivatives. `mediaImageSourceForTreatment` presents that set to the browser; listing three URLs in `srcset` does not mean all three are automatically downloaded. Browser choice depends on slot size and pixel density ([responsive image guidance](https://developer.mozilla.org/en-US/docs/Web/HTML/Guides/Responsive_images)).
- **Different slots:** CaseStudyCard supplies `(max-width: 900px) 100vw, 50vw`; the detail hero supplies `100vw`. This explains the measured 1200 → 1800 desktop selection. At 390px/DPR2, both selected 1200px in the touch sample. Source `sizes` are hints, not measured geometry: the successful desktop detail was actually 1240px wide at a 1440px viewport. Better hints deserve checking, though 1240px still exceeds the existing 1200 candidate, so changing that hint alone would not guarantee a smaller file at DPR1.
- **Clone reuse already exists:** `startFeaturedMediaTransitionFromRole` prefers the source image element's `currentSrc`, intentionally avoiding a new full-size request during flight. There is not an independently necessary third “animation image.” Preserve this behavior.
- **Texture is not just resolution:** the browser bake renders each target width separately with an 11px halftone cell rather than resizing one master baked raster; the PHP path also has fixed-cell treatment generation. Scaling one shared raster at different display sizes can therefore alter apparent dot density and pattern sampling. Do not treat visual equivalence as established.

### Options Worth Comparing
| Strategy | Potential experience benefit | Main tradeoff |
| --- | --- | --- |
| Keep responsive set; align prefetch with actual treatment/size | Makes useful preparation more likely; avoids warming a different treatment | Card and full-size hero may still legitimately need two sizes |
| Choose a common per-device asset for card and detail | One cached URL can serve both and eliminate a late swap/request | Larger card download may slow first appearance; needs a clear shared sizing policy |
| Keep source-sized image through reveal, upgrade after readiness | Maintains uninterrupted imagery while larger image loads | May show transient softness or a texture change; adds handoff complexity and requires direct-entry behavior |
| Use one fixed large file everywhere | Simple cache identity, no resolution switch | Overserves narrow/low-density views and can worsen initial display; not recommended without evidence |
| Use one fixed small file everywhere | Fast small download | Can degrade large/high-density imagery; conflicts with visual-quality requirement |

USCIS measured bodies: the 1200px treatment is 1,331,677 bytes; 1800px is 2,986,242 bytes. A journey that needs both transfers ~4.32MB of these two assets, compared with ~2.99MB if it starts with and reuses only the larger one. The latter saves ~1.33MB over that two-treatment journey but asks the card to load a file about 2.24 times as large initially. This is arithmetic, not a tested speedup. The original's additional 2,465,655 bytes are a separate treatment-selection issue. Asset identity, priority, caching, and when the visitor clicks matter more than simply counting files.

Recommendation: first align treatment-aware warming and inspect size hints. Then compare common per-device reuse against responsive card→detail loading using the same visual composition and throttled journey. Keep the three generated sizes during the experiment; changing which one is selected does not require deleting CMS derivatives. Evaluate modern encoding separately for faster readiness at equivalent detail/texture, without assuming lossless or visually lossless compression ratios. Do not return to runtime halftone generation just to reduce stored variants.
