Chrome CPU is the sum of ten stable, owned process counters; CPU seconds can include simultaneous work on multiple cores. Sampling is approximately once per second, with~60ms enumeration overhead and interpolation at the boundaries. It is not an exact main-thread task breakdown. The already-defunct updater PID60125 contributes zero observed CPU in the measured span and is excluded; other apps' Chrome processes are not included. GPU-process CPU time is CPU-side graphics work, **not hardware GPU time**.

Filter minus original total CPU varies from −0.203 to +0.230 seconds across the six counterbalanced blocks, averaging +0.011 seconds. This does not establish a meaningful CPU advantage or penalty. Trails-off uses 0.612 seconds less on average (about21%); all six paired differences favor off. Shifting CPU window boundaries by±0.5seconds preserves these qualitative results.

The Apple sampler saved 249 valid delta samples over 126.73 seconds, exit 0 and no stderr; all thermal states are Nominal. Reported power is estimated, whole-device CPU/GPU power, including other applications and OS composition. It is not isolated page power or total wall/battery power. Values use the sampler's mW fields; energy/duration reproduces power within rounding, and the installed executable labels these fields in mW. Apple's installed manual explicitly cautions that estimates may be inaccurate and are not for comparisons between devices.

## New Tile-Budget Evidence
Chrome stderr contains 902 tile-memory-limit warnings, all from page renderer PID 59941. Within the measured navigation windows: **741 original, 13 filter, 0 off**. Every original round has 103–136 warnings. The filter has zero in all six forward flights and 13 across two reverse flights (5 and 8); its other four round trips have none. These are warning occurrences, not independent frames or visible flashes.

The retained trace prefix includes the user-confirmed failing original guard. Between its forward activation and reverse settlement, the page renderer records 459 `TileManager::AssignGpuMemoryToTiles` events; 108 explicitly report `had_enough_memory_to_schedule_tiles_needed_now: false`. There are 531 `TileBasedLayerImpl::AppendQuads checkerboard` events. These corroborate missing render tiles internally. No synchronized film maps each event to a physical flash; checkerboard events can occur multiple times per frame/layer.

[Exact Chrome153 tile-manager source](https://chromium.googlesource.com/chromium/src/+/199a3a541d76237379e353b348e64045584db057/cc/tiles/tile_manager.cc#1025) emits this warning when a NOW-priority tile cannot fit after lower-priority resource eviction. Limits consider memory bytes and resource count. This means Chrome's tile scheduling budget cannot accommodate all needed work; it does **not** establish that the Mac has exhausted physical RAM. The sample does not expose the exact allocation limit or resource retention responsible.

Working explanation: eight changing trail surfaces create a tile/resource demand problem in the failing rendering configuration; changing the composition path with the reference filter largely suppresses those failures while increasing GPU work. S18's default→CA-disabled→default reversal remains complementary evidence of renderer dependence. Whether CA resource retention, allocation policy, scale/cadence or another interaction causes the budget failure is still a hypothesis. Missing tiles also need to be related to earlier whole-plane/title/panel loss before declaring the exact mechanism solved. The next causal investigation should target this budget/presentation connection rather than another prefetch patch or generic layer promotion. Do not increase a browser-wide budget or disable rendering features as a website fix.
